# 两站一后台与系统控制台契约

状态：用户于 2026-08-14 确认采用“两套网站、一个后台系统”；本文件是未来员工工作台公网入口、管理员系统控制台、引擎/API 管理和服务器监控的权威规划基线。

## 1. 目标与边界

系统分为两个互联网可访问的网站，但不建设两套重复业务系统：

1. **员工工作台**：面向不超过 10 名公司员工，承载项目、素材、术语、ASR/OCR、前置审改、字幕验收和交付业务。
2. **系统控制台**：只供部署所有者和未来管理员使用，承载引擎/API、提示词/热词、路由、服务器、Worker、队列、存储、预算、日志、告警和审计。

两个网站使用独立前端入口和独立访问策略，共用同一模块化后端、PostgreSQL 领域事实、对象存储和任务系统。两个网站不等于两台服务器；首期允许部署在同一组资源上，未来按负载分别扩容 HTTP、Worker 或媒体处理节点。

## 2. 互联网访问与无自建账号方案

“公开到互联网”在本项目中表示员工可从任意地点通过公网域名访问，不表示任何陌生人可以匿名操作。

首期不开发应用内账号、密码、邀请、找回密码或成员后台，采用 Cloudflare Tunnel + Cloudflare Access 作为应用外身份入口：

- 员工工作台使用单独的 Access Application，只允许显式登记的员工邮箱；员工通过邮箱身份验证进入，不在本系统保存密码。
- 系统控制台使用另一 Access Application，只允许部署所有者的精确邮箱；员工白名单、邮箱域名或“所有有效邮箱”不得继承到控制台。
- 两个 Application 使用不同的 Audience；后端分别校验 `Cf-Access-Jwt-Assertion` 的签名、issuer、audience 和有效期，不能只相信请求头存在，也不能只靠隐藏网址或前端路由隔离。
- 访问身份可以作为审计操作者写入业务命令和控制台变更记录，但不因此建设完整成员/角色数据库。未来账号体系启用后再迁移为正式成员身份。
- 后端源站不直接暴露公网端口；公网流量通过 Tunnel 到达源站。任何绕过 Access、缺少有效 JWT 或 audience 不匹配的请求均拒绝。
- 自动 Worker、部署脚本和未来甲方接口使用独立的服务凭据或内部连接，不复用人的邮箱会话。

员工站若暂时无法提供员工邮箱名单，只能使用匿名 fake 数据和零付费引擎作为演示环境；不得在完全匿名入口上传真实公司素材、开放删除/导出或调用付费 API。

## 3. 两个网站的职责隔离

### 3.1 员工工作台

员工只完成生产任务，不看到以下入口：

- 供应商密钥、Secret 引用和连接凭据；
- 全局引擎启停、模型路由、预算和并发硬上限；
- 服务器终端、容器、数据库维护、备份与恢复命令；
- 跨项目学习库、完整供应商请求载荷和其他员工审计记录；
- 系统控制台的导航或管理 API。

业务页面只显示完成当前任务需要的稳定事实，例如“模拟识别”“主引擎不可用，已转备用引擎”“本月额度已阻断新任务”，不能让员工直接改变全局策略。

当前研发主线只建设这套员工工作台及其业务 API：创建项目、上传素材、确认术语、发起云端识别、查看进度、处理失败和继续后续工作流。供应商选择、并发、预算、服务器和 Secret 配置不以“临时设置页”塞入员工站；当前后端只保留稳定的策略读取/Adapter 接口和开发默认配置，未来再由独立管理员网站通过管理 API 提供生效版本。

### 3.2 系统控制台

控制台采用独立 `ControlShell` 和模块注册表，不混入员工 `AppShell`。两个网站复用同一品牌、颜色、表格、状态、确认框和无障碍规则，但控制台顶部持续显示“系统控制台”，使用独立域名和浏览器标题，避免误把管理动作当成业务操作。

本节是后续对接契约，不代表当前立即开发管理员网站。员工业务 API 与未来管理 API 使用独立路由域和授权 audience；当前业务切片只需从后端策略接口读取已经生效的默认值，不实现管理表单、配置发布、服务器操作或管理员前端。

控制台一级分区固定为：

| 分区 | 管理内容 | 首期写能力 |
| --- | --- | --- |
| 总览 | 引擎健康、任务积压、失败/需对账、费用、服务器和存储告警 | 只读与跳转 |
| 引擎与 API | ASR、OCR、术语 AI、自建引擎的供应商、适配器、模型、语言、连接状态 | 登记、停用、连接测试；不展示明文密钥 |
| 路由策略 | 业务环节对应的主引擎、备用引擎、超时、有限重试、熔断和小流量测试 | 草稿、测试、发布、回滚 |
| 策略与学习 | 本地规则包、AI 快速筛选策略、提示词模板、热词/风险词库、项目术语投影规则、人工学习候选 | 不可变版本、差异、离线评测、小流量测试、发布、回滚；不能直接自动学习上线 |
| 服务器与运行环境 | 环境、服务器、CPU/GPU/内存/磁盘、Worker、队列、数据库、对象存储和备份状态 | 首期以只读监控和安全启停 Worker 为主 |
| 预算与限额 | 日/月预算、调用/时长/字符额度、并发、队列长度、预警线和硬阻断线 | 版本化修改和明确生效时间 |
| 日志与质量 | 请求标识、供应商、模型、耗时、错误、费用、识别质量、术语命中和对账 | 查询、筛选、脱敏导出 |
| 密钥与安全 | Secret 引用、可用状态、最后轮换、连接测试和 Access 入口状态 | 引用绑定和轮换提示；不回显明文 |
| 变更与审计 | 谁在何时修改了什么、旧值/新值、发布版本、失败原因和回退目标 | 只追加、不可覆盖 |

控制台总览不是所有设置的巨型表单。总览只显示异常、容量和费用摘要；具体配置进入对应详情页，低频高级项使用标签页或侧栏渐进展开。

### 3.3 已确认的 ControlShell 视觉与总览基线

用户于 2026-08-16 确认以“成熟企业控制台 + 轻量科技感”的日间控制舱作为唯一生产方向。该方向是后续 UI、前端和真实数据接入的最低质量线，不是只供演示的静态大屏，也不允许生产实现因省事而退化成通用后台模板。

设计验收材料必须逐页说明“未来真实数据源 / 允许操作 / 非目标”，用于约束 UI、前端与后端交接；这些工程注释不是管理员的生产界面内容，正式页面与最终用户预览不得把它们作为可见说明卡直接呈现。生产总览优先使用中文业务术语（例如“当前生效”“执行记录”），provider、adapter、requestId 等技术身份只在确有诊断价值的详情、日志或审计区域展示。

视觉语言固定为：冷灰白主画布、深石墨蓝侧栏与系统运行带、既有靛蓝 `#4458D8` 作为主要动作与选中态、绿/橙/红只表达健康/预警/故障。科技感来自实时状态、精确网格、资源池与趋势，不使用霓虹、玻璃拟态、粒子背景、夸张发光或营销式大卡片。系统控制台是主产品名；“海外短剧字幕生产系统”只可作为小号生态说明，不能与主标题争夺品牌层级。

总览在 `1440×900` 的信息顺序固定为：

1. `ControlShell` 左侧分组导航：系统总览；引擎与 API、路由与调度、服务器与运行环境；策略与学习、预算与限额；日志与质量、密钥与安全、变更与审计。
2. 顶部环境与全局状态条：环境、系统整体状态、最近刷新、自动刷新、待发布变更、全局搜索、告警和当前所有者。刷新时间与自动刷新归为同一状态组，不堆叠重复控件。
3. 深色“系统运行带”：首版必须真实覆盖 `ASR API / OCR API / OCR 自建 Worker / 交付生成` 四个已存在或即将接入的资源池；视频转码启用后作为独立资源池接入，不复用 OCR/交付的容量参数。每个资源池至少显示健康、排队、运行、吞吐或资源占用、今日错误、预算/用量、当前生效配置和“是否暂停接收新任务”。
4. 运行指标带：今日处理剧数、已处理集数、当前运行、失败、需对账、今日调用费用、本月预算和存储使用。费用未知必须显示“待对账”，不能记为零。
5. 趋势与异常：吞吐、队列积压、费用三类事实全部保留；宽屏可以并列，`1024×768` 必须改为一个主图配指标切换或上下布局，不能压缩成不可读的小图。异常队列按严重度、时间和影响范围排序，每条最多一个主操作，其余动作进入次级按钮或详情。
6. 待发布配置与最近变更审计：总览只展示配置名、变更摘要、风险、当前阶段、下一安全动作和最近发布/回滚结果。完整 `draft → testing → impact_checked → approved → active / rolled_back` 流程进入变更详情页；删除不得作为醒目的并列主操作。

截图中出现的字段与模块都属于目标能力，不因响应式改排、渐进展开或详情下钻而删除。正式实现必须把每个数字、状态、版本、费用、请求标识和操作绑定到 PostgreSQL/监控摘要/领域命令的真实来源；没有数据时显示加载、空、失败、未知、过期或未启用，禁止用匿名示例、前端常量或推算结果冒充生产事实。“匿名示例数据”只允许在仓库外设计原型中以一个全局标识出现，不在每个区块重复。

生产一致性门：UI 先交付 `1440×900` 与 `1024×768` 的同状态总览，以及引擎/API、路由与调度、日志与用量、服务器与 Worker、高风险配置发布五个详情方向；前端必须提供同状态、同视口对照。结构、信息层级、深浅关系、资源池运行带、密度和状态语义不得低于确认基线；允许的“更好”只包括更清晰、更易读、更可恢复和更符合真实数据，不包括删功能或改成另一套视觉。

## 4. 引擎和 API 控制平面

- 所有供应商通过统一 Adapter Registry 接入；业务任务只引用稳定的引擎部署标识，不引用厂商 SDK 对象。
- 正式生产 ASR 默认只走云 API，不把本地 GPU ASR 作为首期生产容量来源；本地 fake/stub 继续只负责开发和回归。未来若重新引入本地 ASR，必须作为新的引擎部署单独评估和授权，不能与云 API 共用未经验证的容量参数。
- OCR 同时保留云 API 与自建 Worker 两种 Adapter 能力；是否启用云 API 由真实样本的中文画面字质量、时间轴效果、单集费用和供应商限额共同决定。切换路由不得改变项目、批次、候选和人工裁决的数据契约。
- 每个引擎部署保存 `provider / adapter / model / language / configDigest / capabilities / secretReference / status`；员工不能在创建任务时任意传入未批准厂商。
- ASR、OCR、术语提取、规则检查和未来本地模型是不同能力类型，共用控制平面，但各自拥有独立输入、结果和质量契约。
- 路由策略按“业务环节 → 主部署 → 备用部署”解析。自动降级只适用于已知未受理或无付费副作用的失败；供应商可能已受理但结果未知时进入 `reconciliation_required`，不得自动重复付费。
- 连接测试、样本测试和生产发布是三种不同动作。测试结果不能自动成为生产配置；生产标签始终指向一个不可变版本，并允许回退。
- 管理员可以停用新任务入口，但停用不得删除历史批次、结果、Cue、用量和审计事实。

### 4.1 启动数量与实际执行并发

- 员工选择的是“同时启动哪些剧/项目”，不是服务器线程数；系统允许多部剧同时进入队列，并为每部剧分别显示总集数、已完成、运行、排队、失败和需对账数量。
- 系统控制台单独管理实际执行槽位，首版至少分为 `ASR API`、`OCR API`、`OCR 自建 Worker` 和 `交付生成` 四个资源池；视频转码启用后作为独立第五资源池接入。一个资源池的并发不得作为另一个资源池的默认值。
- 每个 API 资源池至少有五层限制：全局在途请求数、单供应商/部署在途请求数、单项目在途请求数、供应商速率/配额和队列上限；最终生效值取所有适用限制中的最小值。
- “同时启动 20 部剧”可以只意味着 20 部剧都已受理并排队，不表示同时向供应商发出 20×每剧集数个请求。调度器按项目公平领取集级任务，员工页面不得把排队误报为正在识别。
- 管理员调整并发后只影响尚未领取的新集级任务；已被供应商受理的请求继续完成，除非管理员另行执行有确认提示的取消。降低并发不得杀死运行中请求，暂停新任务不得删除队列。
- 并发、速率、预算和路由都使用不可变配置版本并记录生效时间、操作者和旧值/新值；进程重启后必须从 PostgreSQL 恢复当前生效版本，不读取浏览器本地设置。

## 5. 本地规则、AI 快速筛选、提示词、风险词与“微调”分层

控制台必须把以下能力分开，避免把所有优化都叫“微调”或把一次人工修改直接变成生产规则：

1. **本地确定性规则**：字幕格式、时间范围、术语命中、文本规范化、对齐阈值、风险词匹配和无需付费的快速筛选。规则包必须可解释、可离线回放，并作为默认第一层。
2. **AI 快速筛选策略**：只处理本地规则不能稳定判断、命中指定风险或被管理员抽样的条目；允许配置关闭、仅建议、人工复核和小流量验证，不直接拥有最终字幕。
3. **轻量配置**：热词、PhraseSet、提示词模板、后处理规则、风险词、阈值和识别参数；可以快速版本化、测试、发布和回退。
4. **部署配置**：供应商、模型、区域、语言、主备路由、超时、并发和预算；变更只影响新任务。
5. **训练/微调**：使用经过授权的训练集、调优集、隔离评估集和算力产生新模型版本；必须独立立项、授权数据和预算，不能由普通设置开关或一次人工反馈直接触发。

### 5.1 本地规则与 AI 共存策略

- 生产默认执行顺序为“本地规则筛选 → 可选 AI 复核 → 人工决定”。本地规则质量达到已发布评测门槛时，可以把 AI 策略设为关闭或只抽样；AI 关闭、超时、限额耗尽或失败时，条目回到人工队列，主工作流不得瘫痪。
- 本地规则与 AI 输出使用同一条中立建议契约，至少包含建议动作、置信/适用范围、命中证据、是否需要核听、规则或模型版本和来源摘要。二者都只能形成建议或系统筛选事实，不能覆盖已有人工决定。
- AI 只读取当前任务允许的最小上下文，例如公司稿、ASR、相邻轴、已确认术语版本和必要视频时间范围；普通员工页面不显示供应商、模型、提示词全文或密钥。
- AI 不是强制付费门。管理员可按模块、环境、项目标签或抽样比例选择 `local_only`、`local_then_ai`、`ai_review_sample`；策略变更只影响新创建的筛选运行。
- 每个筛选运行固定本地规则包、AI 策略、提示词模板、风险词库、项目术语版本、引擎部署和模型身份。任一配置后续升级都不改写历史建议，也不使已经形成的人工决定自动失效。

### 5.2 策略与学习中心的信息架构

“策略与学习”是一个一级分区，内部使用以下页签，不把全部设置堆在总览：

| 页签 | 管理对象 | 主要动作 |
| --- | --- | --- |
| 本地规则 | 各业务模块的规则包、阈值、适用范围和解释 | 新建草稿、差异对比、回放测试、发布、回滚 |
| AI 筛选 | 模块路由、启停、触发条件、抽样率、模型部署和失败降级 | 样本测试、小流量测试、发布、停用 |
| 提示词模板 | 术语提取、前置审改、风险审查等用途的模板与结构化输出约束 | 新建版本、变量校验、预览、评测、发布、回滚 |
| 热词与风险词 | 公司热词包、风险词库、项目术语投影和规则优先级 | 导入、去重、冲突检查、版本发布、回滚 |
| 操作日志库 | 长期结构化人工操作、系统建议、最终决定、来源与版本身份 | 检索、聚合、脱敏导出；原始事件不可修改 |
| 优化智能体 | 基于日志库、历史规则和评测结果运行的长期优化任务 | 选择范围、目标和预算，运行分析，生成候选；不能直接改生产 |
| 学习候选 | 优化智能体或人工从长期日志归纳的项目建议和跨项目隐藏候选 | 查看证据、合并、批准、驳回、转入评测集 |
| 评测与发布 | 固定回归集、候选版本、质量/费用/耗时差异和发布记录 | 运行评测、批准、小流量、正式发布、回滚 |
| 训练与微调 | 经单独授权的数据集、训练任务、模型版本和评估报告 | 只在另行授权后创建；普通管理员配置不能直接启动 |

### 5.3 人工反馈到生产规则的安全链路

人工操作先长期保存为不可变学习事件，至少绑定项目、集数/轴、来源摘要、系统建议、最终人工决定、规则/提示词/模型版本和必要证据。单条事件只进入日志库，不立即生成或发布新规则；管理员手动启动、或未来明确启用的定期优化任务，才按选定时间范围和模块批量分析。随后按以下单向流程推进：

```text
长期操作日志库 → 优化智能体批量分析 → 项目建议 / 跨项目隐藏候选
              → 脱敏数据集版本 → 离线回归评测 → 管理员批准
              → 小流量验证 → active 版本
```

- 项目内建议可以帮助同项目后续条目，但不能静默重写已完成字幕。
- 跨项目候选只有达到最小证据量、人工批准且通过固定回归集后，才能成为公司级规则、风险词、热词投影或提示词新版本。
- 生产质量必须同时比较误报、漏报、人工处理量、费用和耗时；不能只看模型自报置信度或“采用率”。
- 每个生产版本都必须记录来源事件集合、评测报告、批准者、生效范围、前一版本和可回滚目标。发现回归时一键回到上一 `active` 版本，不删除失败版本和审计记录。

项目术语版本仍属于项目业务事实；控制台只管理“如何把项目术语确定性投影为各厂商热词”的公司级规则和限制。普通日志只保存 digest、数量和版本，不复制整份敏感术语。

### 5.4 长期优化智能体

优化智能体是系统控制台内的独立后台能力，不是员工聊天框，也不是会自行改代码或生产配置的“自我升级模型”。首版按持久化批处理任务设计：

- 管理员选择业务模块、项目范围、时间范围、问题目标、最小证据量、费用上限和使用的分析模型后创建一次优化运行；运行可暂停、失败恢复、查看进度和重放同一输入快照。
- 智能体读取结构化事件、历史规则/提示词版本、此前候选的批准或驳回结果和固定评测报告；数据量大时先由 PostgreSQL 聚合、去重和抽样，不把整个日志库一次塞入模型上下文。
- “长期记忆”保存为可审计的事实：事件索引、已批准/已驳回候选、稳定摘要、评测结果和版本关系；不依赖浏览器会话，也不保存或宣称能读取模型隐藏思维过程。
- 智能体只能输出候选规则、候选风险词、候选提示词补丁、异常模式、建议测试案例和预估影响；这些产物先进入草稿/候选区，不能直接调用发布接口。
- 每个候选必须能回到支持与反对它的匿名事件集合，并显示覆盖量、误报风险、可能节省的人工量、预计 AI 费用和未知项。没有证据的“经验总结”不能进入评测。
- 管理员的采用、修改或驳回会作为后续优化运行的反馈，但同样只形成新事实；智能体不得为了迎合历史采用率而绕过固定回归集。
- 首期使用同一 PostgreSQL 保存事件、任务、检查点、候选和评测元数据；只有真实规模证明事务库查询成为瓶颈后，才另增分析库或向量索引，不预先拆新服务。
- 原始音频、视频和完整供应商载荷默认不进入长期日志库。需要音频微调时，另建获授权的数据集任务、保留策略和隔离评估，不能由优化智能体自动收集。

管理 API 只提供结构化动作：创建/读取/取消优化运行，浏览事件聚合与候选，创建不可变草稿版本，运行离线评测，批准、发布和回滚。普通员工业务 API 无权查询跨项目日志或调用这些接口。

## 6. 服务器与运行环境控制

- 服务器列表按环境组织，首期至少区分本地开发、内部测试和未来生产；环境、服务器、应用、Worker 和存储是不同层级。
- 总览显示健康、CPU/GPU/内存/磁盘、队列深度、运行/失败任务、数据库连接、对象存储容量、备份结果和最近告警。
- 容量参数使用配置而非散落常量：HTTP 实例数、各类 Worker 并发、单服务器任务槽、队列上限、磁盘水位和自动暂停阈值均可追溯。
- API 型 Worker 主要受供应商并发、速率、网络和预算约束；自建 OCR Worker 主要受 CPU/GPU、显存、抽帧量和模型实例数约束。控制台必须分别展示“排队项目/集数、当前在途 API 请求、当前本地运行任务和最近吞吐”，不能只展示一个模糊的总并发数字。
- OCR 走云 API 时，允许先在受控 Worker 中完成抽帧、画面变化筛选和相似帧去重，再只提交需要识别的候选帧；原始帧数、提交帧数、去重率和供应商计费数量都进入用量证据，避免把无变化画面重复计费。
- 首期允许安全启停 Worker、暂停接收新任务和查看健康，不直接提供裸 SSH/Web Terminal、任意命令、删除服务器、购买资源或修改防火墙。
- 扩容、缩容、换规格、删除服务器、恢复数据库和清理对象等高风险动作必须展示影响范围、当前任务、回滚能力和二次确认；接入云厂商写 API 前另过授权门。
- 系统控制台展示本站需要的摘要与操作；高级容器、系统指标和告警可深链到 Coolify/Portainer/Grafana 等专用平台，不在业务项目内重造完整服务器管理产品。

## 7. 配置生命周期与唯一状态源

配置统一采用：`draft → testing → approved → active → retired`。

- 每次修改创建不可变版本，不直接覆盖当前生效内容。
- `approved` 只表示已经通过规定评测和人工批准，不等于已经影响生产；小流量或定时发布仍须创建明确发布命令。
- `active` 只是指向某个版本的唯一指针；发布失败保持旧版本生效。
- 任务创建时固定实际使用的引擎部署、路由、提示词/热词规则和预算策略版本；后续修改不重写历史任务。
- 浏览器表单和图表只是展示/草稿，PostgreSQL 是配置版本、发布指针、用量和审计的权威来源；服务器指标存于时序/监控系统，控制台读取稳定摘要。
- 所有写操作使用幂等命令和并发版本；未知结果不得提示成功，失败后保留输入并提供唯一恢复动作。

## 8. 日志、隐私和费用

- 默认保存请求元数据：项目/任务标识、引擎部署、模型、状态码、耗时、计费数量、金额、重试、对账和配置版本。
- 原始视频、完整字幕、完整提示词、完整热词和供应商密钥不进入普通运行日志。需要问题取证时使用明确开启、短保留和脱敏的诊断模式。
- 预算区分提醒阈值与硬阻断；界面必须明确软预算是否仍继续调用，不能把提醒伪装成费用上限。
- 费用未知显示“待对账”，不能显示为零。每次付费调用可追溯到项目、任务、供应商请求标识和最终用量。
- 用量与费用页必须同时支持逐 Attempt 明细和按项目、日期、供应商、模型聚合；字段至少包含媒体时长、计费单位/数量、预估金额、最终金额、币种、对账状态、热词 payload 摘要和供应商请求标识。员工工作台不复制这张管理表。

## 9. 分阶段交付

### 控制台地基

- 两套独立前端入口与后端访问域；
- 外部邮箱身份、两个 Access audience 和后端 JWT 校验；
- 引擎登记、fake/stub 连接测试、路由/提示词/热词版本骨架；
- 本地规则包、AI 筛选策略、风险词库、学习候选、评测与发布的版本骨架；
- Worker、队列、服务器、数据库和存储只读健康摘要；
- 预算、用量、日志和不可变变更审计。

### 真实 API 小样本阶段

- 用户批准具体厂商、密钥引用、预算和 1–3 集匿名/获准样本；
- 对比中文准确率、术语命中、时间轴、异常长段、失败恢复和费用；
- 测试通过后显式发布主部署/备用部署，不自动替换。

### 生产运维阶段

- 服务器扩缩容、备份恢复、云厂商写 API、训练/微调和未来管理员角色；
- 这些能力分别授权，不由“控制台已经存在”推导出自动执行权限。

M3 员工内部工作台与真实素材冒烟已经关闭。系统控制台现进入正式产品设计阶段；仍按“UI 生产基线 → 管理 API/权限域 → 正式前端 → 两站真实接入”分切片交付，不以一张总览图替代详情、状态矩阵或真实数据链。

## 10. 参考模式

- Cloudflare Access：自托管应用身份代理、独立 Application Policy 与 JWT 验证。
- LiteLLM / Portkey / Cloudflare AI Gateway：多供应商登记、统一路由、预算、限流、日志和降级。
- Langfuse：提示词不可变版本、环境标签、测试、发布和回滚。
- Coolify / Portainer / Grafana：服务器资源清单、环境分组、指标、健康与告警。
- Google Speech Adaptation / Amazon Transcribe：热词/词表增强与真正自定义模型训练分离。

以上只作为成熟模式参考；本项目保留自己的业务状态机、项目术语版本、人工证据和付费幂等边界，不直接嵌入第三方控制台作为业务权威来源。
