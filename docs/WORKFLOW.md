# 四角色协作与同步协议 v4.4

状态：生效  
最后更新：2026-08-15

## 1. 目的

让规划、UI 设计、后端开发和前端开发四个 Codex 对话围绕同一个仓库、同一套产品契约和同一份当前看板协作。用户负责产品取舍和必要授权，不负责复制聊天内容、转述交接或判断哪个对话该继续。

本协议的核心不是“多开对话”，而是建立一条有依赖、有验收、有回退的交付流水线：

```text
用户决策 / 规划契约
        ├── UI 交互设计 ──────┐
        └── 后端状态与接口 ───┼──> 前端生产实现 ──> UI 视觉验收 ──> 规划端到端验收
                              └──> 后端独立验证
```

允许 UI 与后端在输入稳定、文件范围不重叠时并行；前端只有在依赖的 UI 交付和后端契约都达到看板要求后才能集成。任何角色不得自行填补上游未确认的产品规则。

## 2. 四个固定角色

| 角色 | 负责 | 不负责 | 主要交付物 |
| --- | --- | --- | --- |
| 规划对话 | 产品需求、范围、优先级、成本、里程碑、业务状态含义、跨模块契约、任务拆分和最终端到端验收 | 编写业务代码、替 UI 决定详细视觉、私自购买或部署 | `PRODUCT.md`、里程碑、文档契约、ADR、架构、`CURRENT.md` 任务分派 |
| UI 设计对话 | 信息架构、用户流程、页面布局、交互状态、设计变量、原型、截图和视觉验收 | 修改后端状态含义、编写生产 React 页面、修改数据库/API | `DESIGN.md`、`docs/ui/`、仓库外原型与截图验收 |
| 后端开发对话 | PostgreSQL、迁移、Fastify API、共享代码契约、存储、Worker、幂等与后端测试 | 修改生产前端、重新设计 UI、擅自改变产品范围 | `backend/`、`backend/migrations/`、`packages/contracts/`、`tests/backend/` |
| 前端开发对话 | React/Vite 生产页面、浏览器文件处理、API 消费、前端状态投影、可访问性和前端测试 | 修改数据库、后端路由、共享契约含义、另建一套业务状态 | `frontend/`、`tests/frontend/`、前端真实浏览器验证 |

历史任务中的 `DEV-*` 和“开发对话”保留为历史事实；v3 以后新任务分别使用 `BACK-*` 和 `FRONT-*`，不再创建含混的全栈开发任务。

## 3. 单仓库和同目录协作

- 四个对话使用同一个保存项目 `七猫兼职`，业务仓库固定为 `qimao-terms-cloud/`。
- 当前 M2 主线存在尚未提交的连续实现，所有角色必须读取同一工作目录中的最新文件；未经规划和用户明确批准，不为角色协作另建仓库、复制项目或隔离 worktree。
- 一个代码仓库只保留一套当前源码。前后端通过 `packages/contracts/` 和后端 API 对接，不通过复制类型、复制状态机或聊天约定对接。
- Git 提交、分支、远程、推送和部署仍需用户明确授权；任务分派不构成版本操作授权。

## 4. 文件所有权与写入边界

| 范围 | 默认唯一写入角色 | 其他角色如何协作 |
| --- | --- | --- |
| `PRODUCT.md`、`docs/milestones/`、`docs/contracts/` 的业务语义、`docs/architecture.md`、成本/ADR | 规划对话 | 提交阻塞证据或变更请求，不直接改写产品含义 |
| `DESIGN.md`、`docs/ui/`、仓库外 UI 原型与截图 | UI 设计对话 | 规划给范围；前端读取并实现；后端不得改视觉规则 |
| `backend/`、`backend/migrations/`、`tests/backend/` | 后端开发对话 | 前端通过 API 使用；发现缺口时退回契约请求 |
| `packages/contracts/` | 后端开发对话 | 规划拥有语义，后端实现代码契约；前端只消费，不复制或私改 |
| `frontend/`、`tests/frontend/` | 前端开发对话 | UI 做验收不直接修代码；后端不修改前端页面 |
| 根级 `package.json`、锁文件、工作区与测试配置 | 看板明确指定的集成责任人 | 未指定时不得顺带修改；需要跨角色改动时拆独立任务 |
| `docs/status/CURRENT.md`、`docs/logs/DEVELOPMENT_LOG.md` | 所有角色按任务写入 | 只能更新自己当前任务的行和追加本轮日志；新建、删除、改优先级由规划负责 |

强制规则：

- UI 设计任务不得修改 `frontend/src/`；如果需要生产实现，必须交给独立 `FRONT-*` 任务。
- 前端不得修改 `backend/`、迁移或 `packages/contracts/`。接口不足时，把前端任务设为 `blocked`，写出期望输入、实际响应和最小契约缺口，交给规划或后端。
- 后端不得修改 `frontend/` 来“顺便接通”；只交付稳定契约、接口、错误结构和验证证据。
- 规划不得编写业务实现；规划只固化含义、依赖、验收和任务状态。
- 同一个生产文件在同一时刻只允许一个活动任务拥有写入权。若两个角色需要同一生产文件，规划必须拆成有先后关系的任务。`CURRENT.md` 与开发日志是共享协调文件的唯一例外：各角色只修改自己的任务行或追加自己的日志，写入前按全局版本重读；冲突时重新读取并做最小合并，不能覆盖另一角色刚写入的事实。

## 5. 唯一状态源与版本

`docs/status/CURRENT.md` 是唯一当前任务看板。文件顶部必须包含“同步协议”“同步版本”和“最近写入角色”。每个任务必须包含独立 `Rev`。

- 任何角色写入前重读最新同步版本和自己的任务行。
- 每次有效写回都递增全局同步版本。任务 `Rev` 表示“可执行工作包版本”，只有交付内容、验收标准、停止边界或返工轮次发生变化时才递增；单纯领取、通知、Reviewer 回传或规划路由不机械增加 `Rev`。
- 如果版本已变化，先合并最新事实；不得用旧对话记忆覆盖新状态。
- 聊天中说“已交给某角色”不算交接。日志、看板、版本和 `Current actor` 四项同时更新才算交接完成。
- 对话摘要、口头计划和代理结论不是业务状态源。

## 6. 任务字段、状态和角色名称

每项任务必须包含：`ID`、`Rev`、`Owner`、`Current actor`、`Reviewer`、`Status`、`Goal`、`Inputs/Deliverables/Acceptance`、`Boundary/Next`。

`Current actor` 只使用：`规划对话`、`UI 设计对话`、`后端开发对话`、`前端开发对话`、`用户` 或 `—`。

状态只使用：

- `blocked`：缺少明确输入、上游交付或授权，不能开始。
- `ready`：输入齐全，可以领取。
- `in_progress`：Owner 已领取，当前正在处理。
- `review`：交付或验收证据已经形成，正在经过规划交接审计或指定 Reviewer 验收。Owner 完成时先把 `Current actor` 切到规划对话；规划审计通过后，才可以把 `Current actor` 切到 Reviewer。
- `done`：验收通过，不再重复。

`Owner` 对交付负责且退审时不变；`Current actor` 表示现在真正应动作的人；`Reviewer` 负责给出带证据的领域验收结论。规划对话是所有跨角色交接的强制审核与调度中心，即使规划不是该任务的最终 Reviewer，也必须先后两次接收“Owner 交付”和“Reviewer 结论”。一个任务只有一个 Owner 和一个 Reviewer。

## 7. 任务颗粒度

每个任务只交付一个可独立验证、可独立退回的结果，通常应在一次对话工作周期内完成。出现以下情况必须拆分：

- 需要更换角色，例如产品裁决、UI 设计、后端契约和前端实现不能放在同一任务。
- 包含两个可分别验收或分别失败的结果，例如“资产绑定后端”和“上传队列前端”。
- 同时涉及当前切片和下一切片。
- 需要修改另一个角色拥有的文件。
- 涉及购买、部署、远程、推送、付费调用或真实数据授权。

每个 `ready` 任务还必须指向 `docs/contracts/MODULE_RESPONSIBILITY_MATRIX.md` 的一个模块行，并在任务输入中写明 UI 显示、允许目录、权威数据源、明确非目标和验收。若一个任务同时命中两个可独立失败的模块行，必须拆分；导航占位、素材角色名称或未来入口不构成实现该模块的授权。

涉及前置审改、术语、ASR/OCR、风险审查、播放器、字幕验收或交付的任务，还必须指向 `docs/contracts/LOCAL_APP_PARITY.md` 的对应能力行，读取该能力在两个本地应用中的入口、保护规则和测试证据。任务可以优化实现和操作路径，但不得静默删减原能力；发现本地能力没有被共享契约或 UI 表达时，按第 16 节冲突协议暂停并交回规划。

推荐任务链：

1. `PLAN-*`：确认业务规则、状态、依赖和可观察验收。
2. `UI-*` 与 `BACK-*`：输入稳定且文件不重叠时并行。
3. `FRONT-*`：同时消费已验收 UI 和稳定后端契约。
4. `UI-* QA`：只做真实页面视觉/交互验收，不直接修生产代码。
5. `PLAN-* ACCEPT`：跑端到端主流程并确认切片完成，不替代模块测试。

同一根因的返工不新建任务：保持 ID 和 Owner，递增 `Rev`，记录失败证据和复验标准。只有目标、角色或独立交付物发生变化才新建任务。

## 8. 契约优先与前后端对接

- 规划文档定义业务状态含义、用户动作、错误语义和非目标。
- 后端在 `packages/contracts/` 实现唯一代码契约，并通过后端测试证明响应和错误边界。
- 前端只从共享契约和真实 API 读取状态，不手写重复枚举、不根据进度百分比猜业务完成、不使用本地副本决定服务端状态。
- UI 原型中的示例状态不构成 API；前端实现前必须把原型状态映射到共享契约。
- 后端契约变化时先完成 `BACK-*` 并写明版本/字段/错误差异，再允许前端消费。
- 前端发现契约缺口时不增加临时 fallback 掩盖问题；必须提供“页面动作 → 所需字段/错误 → 当前缺口”的最小复现并退回。

### 8.1 已确认 UI → 正式前端一致性硬门

用户确认且由规划关闭的 UI 任务，其 `DESIGN.md`、对应 `docs/ui/` 验收记录和其中指定的最终原型/截图共同构成正式前端的权威设计输入。三者互相冲突时不得自行选择，必须先交规划裁决。该规则适用于当前及后续所有有 UI 的页面、弹窗、抽屉和关键流程。

规划对话是 UI→前端的唯一统筹者：先把已确认设计、真实共享契约和本地能力等价要求整理成单一交接包，再解锁前端；前端交付后由规划先检查“设计项→生产实现→证据”的映射完整性，再路由 UI 验收正式 React。UI 与前端可以提出专业意见，但都只交规划汇总、裁决和版本化，不能各自选稿、私下变更标准或要求用户转述。

1. **UI 交付必须可复现**：至少标明关键页面/状态的最终参考路径、桌面验收视口、状态矩阵、滚动与焦点行为，以及允许由真实数据导致的差异；废弃稿不得继续作为前端参考。
2. **前端不得自行再设计**：信息架构、区域层级、核心操作、状态专属动作和主要交互必须完整对齐；同状态下的布局比例、间距、密度、颜色语义、控件形态和视觉层级应达到肉眼可确认的高一致。未经规划或用户确认，不得以“功能相同”为由删减、重排或替换已确认设计。
3. **真实事实优先于截图造假**：正式页面必须使用真实 API 和真实运行状态。真实集数、媒体不支持、能力未启用、空数据或失败状态可以与示例截图不同，但必须保留设计的同构位置和状态表达；禁止伪造数量、视频、AI/风险结果、成功状态或静态业务数据来追求相似。
4. **前端交审证据**：首次进入规划审核前，前端必须为指定视口提供正式 React 与权威 UI 的同状态截图对照、必要的 DOM/几何/滚动/焦点证据，并列出全部有意差异及其权威来源。只提供单张生产截图、单元测试、类型检查或构建通过不满足本门禁。
5. **无法一致时先冲突审查**：若共享契约、浏览器能力或真实数据使已确认设计无法可靠实现，前端必须在编码前或发现时按第 16 节提交专业异议，由规划决定补契约、退回 UI 或明确接受差异；不得静默降级。
6. **UI 真实页面验收**：UI Reviewer 必须基于正式 React 而非开发自述完成同状态对照。结构、信息层级、主要比例、密度、颜色语义、组件形态或关键交互的明显偏差按 P1/P2 记录并阻止 `done`；操作系统字体渲染等不可控轻微像素差异可作为 P3 记录。
7. **冻结后的变更受控**：UI 冻结后如产品方向发生变化，先更新 UI 任务 Rev 和权威参考，再允许前端跟随；前端实现不能反向成为未经确认的新设计标准。

每个 UI→前端交接包至少包含：权威参考版本与文件路径、关键页面及状态清单、桌面视口、真实数据字段映射、允许差异、前端允许目录、明确非目标、同状态对照要求和最终 Reviewer。任一项缺失时前端保持 `blocked`，由规划补齐，不把缺口留给 UI 与前端在实现中自行猜测。

## 9. 允许并行的条件

只有同时满足以下条件，两个角色才能并行：

- 规划任务已由用户确认，业务含义不再待定。
- 两个任务修改的物理文件集合不重叠。
- 双方依赖的是同一份已版本化文档或代码契约。
- 看板分别给出独立 Owner、Current actor、验收和停止边界。
- 任一方失败不会要求另一方猜测或重写自己的状态源。

当前 M2 推荐并行方式是 UI 设计上传交互、后端实现资产绑定；正式前端集成必须等待这两项输入达到看板要求。

## 10. 规划协商门

涉及产品范围、功能先后、技术路径、成本、文件格式、目录规则、模块对接、外部服务、里程碑或开发切片时，规划必须先与用户讨论：

1. 读取现有事实，提出会改变数据模型、流程或成本的关键问题。
2. 给出具体方案、得到/暂时得不到的结果、风险、开发量和推荐。
3. 首次给出方案时，规划任务保持 `review`、`Current actor=用户`；依赖任务保持 `blocked`。
4. 用户明确确认后，规划任务才可改为 `done` 并解锁下一角色。
5. “继续”或“可以”只确认紧邻上下文已经展示的具体方案，不自动授权尚未说明的后续工作。

不改变范围的状态维护、已确认方案内的机械同步和验收写回不需要重复协商。

## 11. 每个对话的启动动作

1. 读取项目级 `AGENTS.md`、本协议和 `docs/status/CURRENT.md`。
2. 执行权限预检并在首个回执中明确写出：工作区根包含 `C:\Users\ComradeGu\Documents\七猫兼职`，目标仓库处于 `workspace-write` / `:workspace` 可写范围；普通仓库内写入不会经过 `auto_review`。
3. 若权限为 `read-only`、工作区根不匹配，或普通仓库编辑异常触发审批，立即停止并回报 `permission_blocked`；不得尝试绕过、不得把审批失败当成用户未授权。规划负责登记阻塞并修正或重新派发。
4. 记住同步版本，只读取自己最高优先任务列出的必要输入。
5. 找到 `Current actor` 等于本角色的唯一最高优先任务。
6. `ready`：说明任务编号、交付物、文件范围和非目标，写回 `in_progress` 后开始。
7. `review`：直接按验收条件复验并写回结论。
8. `blocked`：只处理边界中明确分派给本角色的解阻输入；否则停止。
9. 没有本角色可执行任务时，报告看板中的真实阻塞，不创建自选任务、不修改文件。

## 12. 标准写回、主动唤醒与七项交接

每次状态变化必须在同一次写回中完成：

1. 在 `docs/logs/DEVELOPMENT_LOG.md` 记录任务 ID/Rev、实际修改、验证、未完成项和边界。
2. 更新 `CURRENT.md` 中该任务的 Rev、Status、Current actor、交付物、验收证据和下一步。
3. 递增全局同步版本，更新最近写入角色。
4. 重新读取任务行，确认接收方可以只凭该行和列出的输入开始。
5. 只向规划总线或 `CURRENT.md` 明确指定的接收对话发送正式唤醒消息；执行角色不得绕过规划直接通知另一执行角色。
6. 发送方必须使用 `read_thread` 或 `wait_threads` 确认消息已经出现在目标任务，且目标进入 `inProgress` 或给出明确接收/停止回执；消息 API 返回成功但目标未被唤醒不算送达。
7. 发送失败、目标未出现消息或未被唤醒时立即重试并记录；重试后仍失败才标记 `notification_pending` 并向规划报告，绝不能让用户代为传话。

交接必须回答：谁完成、完成什么、证据在哪里、什么没完成、为什么转交、现在轮到谁、接收方停止边界。缺一项都不算完成。

交接还必须标明所依据的职责矩阵模块行。接收方发现任务内容超出该行，或把另一个流程阶段塞入当前页面/接口时，应按第 16 节立即停止受影响部分并发起范围冲突审查。

### 12.1 自动通知与接力

`CURRENT.md` 必须维护四个固定角色对应的 Codex 任务 ID。采用“规划总线”模式：UI、前端、后端之间禁止直接接力，任何完成、验收、退审、冲突或下一任务解锁都必须先进入规划对话审核。用户不负责复制任务内容。

1. Owner 交付后写入证据，把任务转为 `review / Current actor=规划对话`，保留既定 Reviewer，只自动通知规划；不得直接通知 Reviewer、下一 Owner 或用户开始动作。
2. 规划把交接登记进 FIFO 队列，先审查任务颗粒度、允许目录、范围矩阵、验收证据、未完成项、依赖、临时数据清理和下一接收者。交接不完整则退回原 Owner；完整才保持 `review` 并把 `Current actor` 路由到指定 Reviewer，由规划发送唯一的跨角色通知。
3. Reviewer 只形成领域验收结论，不自行标记 `done`、不解锁后继任务，也不直接通知原 Owner或下一角色。Reviewer 写入证据后把 `Current actor` 再次切回规划对话并只通知规划。
4. 规划审核 Reviewer 结论与依赖：通过则由规划标记 `done` 并解锁/通知下一任务；不通过则由规划递增 Rev、退回原 Owner 或建立明确的新任务。只有规划对话可以发出跨角色启动、返工和下一环节通知。
5. 发现专业冲突同样只通知规划；规划裁决后一次性通知全部受影响角色。角色之间可以提供证据，但不能绕过规划改变状态或要求对方开始工作。
6. 自动消息只能在状态板和日志成功写回后发送；聊天消息不能先于权威状态，也不能替代权威状态。通知接收者必须重新读取权威文件，不得只相信消息正文。
7. **责任归属**：Owner 负责唤醒规划并确认规划任务已进入运行或明确回执；规划负责唤醒 Reviewer、返工 Owner或下一 `Current actor`，并确认该目标任务已进入运行或明确回执。Reviewer 完成后同样负责唤醒规划并确认送达。任何角色不得把“消息已调用”写成“目标已收到”。
8. **失败重试**：发送失败、目标任务中未出现消息或目标未被唤醒时，发送方必须立即重试并读取目标状态。重试后仍失败才写 `notification_pending`，记录目标任务 ID、尝试次数和最近错误，并只向规划报告；禁止转化为“请用户手动传话”。
9. **三段式完成证据**：每次交接完成汇报必须分别列出“状态已写回”“唤醒已发送”“送达/运行态已确认”。缺少任一项时交接未完成，FIFO 不得关闭，后继依赖不得仅凭文件写回解锁。
10. `Current actor=用户` 仍表示确实需要产品、视觉、成本或数据决策。产品意见可以发生在对应对话，但该对话必须把用户结论写回并交给规划审核，由规划统一完成状态变化和后续通知。
11. **派发权限握手**：规划发出启动、返工或验收消息后，只有目标明确确认“根目录正确 + workspace-write/:workspace 可写 + 普通仓库编辑不走 auto_review”，才算运行态送达；单纯显示 `inProgress` 不足以关闭派发 FIFO。
12. **权限阻塞路由**：目标回报 `read-only`、根目录不匹配或普通写入触发审批时，规划立即将该任务标为 `blocked / Current actor=规划对话`，FIFO 标为 `permission_blocked`，记录目标任务 ID、实际权限和失败动作。规划修正或重新派发后重新完成权限握手；不要求用户传话，也不把权限故障计入业务 Rev。
13. **审批边界**：范围内仓库文件编辑、状态/日志写回和非破坏性测试使用工作区权限直接执行；`auto_review` 只用于工作区外路径、受限网络、外部副作用或购买、真实付费 API、云资源、提交/推送、部署和破坏性操作。

### 12.2 规划接力收件队列

所有交付、领域验收结果、退审和冲突通知都必须到达规划对话；允许同时到达，但规划必须串行处理，不能让后到消息覆盖、打断或混入正在执行的任务。`CURRENT.md` 的“规划接力收件队列”是规划调度的唯一来源；任务看板继续拥有业务状态，队列只记录交接事件的处理顺序，不复制业务结论。

1. **按到达排位**：以任务完成写回后，首次有效自动交接到达规划对话的顺序分配单调递增序号；不按 UI、后端、前端角色写死顺序，也不按规划预想的开发顺序插队。
2. **单一规划审核项，不等于全局串行开发**：规划收件队列最多一个交接事件为 `active`。规划完成当前交接的复验、裁决或状态写回前，后来交接只能登记为 `queued`、`waiting_dependency` 或 `waiting_user`；但任务看板中已经由规划解锁、文件范围互不重叠的 UI、后端、前端任务可以继续受控并行，不受收件队列单活动项限制。同一纵向切片默认最多三个执行任务并行。
3. **阻塞让出执行位**：队首若缺少依赖或需要用户确认，保留原序号并标记等待，不占用 `active`；规划选择序号最小且当前可执行的项目。等待条件满足后，它按原序号在当前活动项结束时重新参与选择。
4. **去重而不吞新返工**：同一任务、同一 Rev 的重复通知合并到原队列项；同一任务的新 Rev 代表新的交接事件，取得新的队尾序号，不能沿用旧序号插队。
5. **完成后再接下一项**：活动项只有在验收结论、日志、看板和同步版本均写回，正式唤醒已发送，并经 `read_thread`/`wait_threads` 确认目标已进入运行或明确回执后才能标记 `closed`；随后才把下一个可执行项改为 `active`。仅调用发送接口、口头回复或只写 `CURRENT` 都不算完成。
6. **用户指令优先但必须留痕**：普通自动消息永不抢占。只有用户明确要求停止、替换或调整当前优先级时，规划才能暂停活动项并调整队列，同时在队列“说明”中记录原因；一般提问和状态询问不自动改变排位。
7. **等待用户不转嫁传话**：`waiting_user` 只用于确实需要用户产品、视觉、成本或数据决定的事项。其他角色的完成消息、返工消息和依赖同步仍由任务间自动通知处理，不能让用户人工复制。
8. **微返工快车道**：同一根因、最多 2 个生产/测试文件、不改 API/共享契约/迁移/业务状态/视觉方向的返工，经规划确认后仍进入 FIFO，但使用压缩交接。Owner 只跑受影响专项与真正必要的类型/构建检查；规划只核对差异和定向回归；Reviewer 只复验变化场景，不重跑完整矩阵、全尺寸截图或既有通过证据。快车道不能绕过规划总线、P0/P1 门禁或切片关闭时的完整质量门。
9. **下一任务预备不等于提前开发**：当前切片终验期间，规划可以把下一任务的输入、目录、依赖和停止边界预先写成 `blocked`，但不能通知 Owner 开始。当前切片通过后，规划必须在同一次状态写回中关闭质量门、把预备任务改为 `ready` 并自动通知；不再额外等待用户传话或空转一轮。

规划收到多个消息时，对外只需分别确认“已入队 + 序号/等待原因”。确认入队不是验收通过，也不改变对应任务的业务状态。微返工快车道可以压缩文字，但仍必须保留到达序号、根因、允许文件、定向证据和停止边界。

### 12.3 阶段简报

规划对话负责向用户提供低打扰、可追踪的阶段简报，不要求用户阅读每一次角色交接。满足任一条件时主动汇报：

- 连续完成 2–3 次跨角色交接；
- 一个纵向切片进入开发、终验或完成的新阶段；
- 出现可能影响最晚交付窗口、成本或核心质量的阻断；
- 距离上次整体简报已满两个自然日。

阶段简报固定回答六件事：当前阶段、按完整内部可用版计算的完成比例、完成事实、阻断与风险、下一执行角色、最晚交付窗口是否受影响。普通领取、测试开始、无变化等待不单独打扰用户。同步版本/FIFO 数量必须明确说明是协作事件数，不得包装成产品版本或功能完成度。

### 12.4 协作持续改进

- UI、前端、后端和规划都可以提出协作改进建议，范围包括任务颗粒度、交接字段、审查顺序、验证成本、工具限制和文档可读性；不得因角色不同压制专业意见。
- 建议必须写明“当前摩擦 → 可验证证据 → 建议规则 → 预期收益 → 新风险 → 试运行期限”，只交规划总线，执行角色不得各自修改协议或创建平行流程。
- 不改变产品范围、成本、数据含义或角色权限的局部流程优化，由规划合并后可试运行一个纵向切片；涉及用户体验、付费、质量下限、角色权限或交付日期的变化必须先与用户确认。
- 试运行结束由规划记录“保留 / 调整 / 回退”及证据，并递增协议主版本或次版本。流程建议不能与业务缺陷混在同一次代码返工中。
- 同一根因的原始失败证据经一次修复后仍在真实复验中失败，即视为连续两次失败；停止第三个局部补丁。规划必须重新审查状态所有者、DOM/数据提交时序和公共实现边界，合并完整缺口后再决定重构、改契约或调整验收。

## 13. 验收和退回

- 后端任务通常由规划复验业务契约与恢复边界；后端自测不能代替规划验收。
- UI 设计通常由用户验收；未获用户确认的视觉方案不能交给前端实现。
- 有 UI 的前端生产任务先由 UI 设计角色做真实页面视觉/交互验收；通过后再由规划执行独立端到端验收任务。
- Reviewer 必须在一个有界批次中检查完整验收矩阵，再一次性交回全部已发现问题；除 P0 数据损坏、重复付费、安全泄露或无法继续外，不因发现第一个缺陷立即结束整轮检查。
- 每个带异步查询或命令的前端交付在首次送 UI 前必须提供状态转换预检：初始加载、稳定失败、失败原因/请求标识/唯一恢复动作、人工重试提交中、重试再次失败、重试成功后的数据与焦点落点、关闭后的原触发点恢复。不存在的状态必须说明原因；只验证“成功数据出现”不能代替焦点、重复请求和恢复语境验证。
- 每个纵向切片最多执行一次完整正式浏览器矩阵。完整矩阵退回后的修复只做与缺陷直接相关的增量真实复验；其他通过项以明确证据路径冻结。只有跨越 API/数据状态/视觉结构的新变更，规划才能重新打开相应矩阵范围。
- 缺陷统一分级：P0 阻断且立即停线；P1 发布前修复；P2 在当前切片集中修复或经规划明确延期；P3 只记录优化，不阻塞内部可用版。
- 实现/返工阶段只跑受影响模块的定向测试和必要构建；纵向切片关闭、数据库迁移合入或内部发布前才运行一次完整 `pnpm check`。同一证据不得由每个角色机械重复。
- 涉及 PostgreSQL 的规划独立复验和切片质量门，在默认库可能被并行浏览器验收、开发服务或其他角色占用时，必须使用本轮创建且名称可验证的隔离临时数据库，从空库应用全部迁移后运行测试；结束时只删除本轮创建的精确临时库。不得为通过测试清空、停止或改写另一角色正在使用的默认库。该规则先在 S2.1 试运行，切片关闭时由规划记录保留或调整结论。
- 单元测试不能替代异步失败、刷新恢复、焦点管理或浏览器文件行为的真实流程验证；真实浏览器受合规工具限制时，规划可以接受等价的可控 DOM/接口测试，但必须记录未取得的动态证据和裁决理由。
- 涉及本地双应用迁移的任务只有在 `LOCAL_APP_PARITY.md` 写回本地来源、云端实现、行为差异和验证证据后，才能从 `review` 关闭；内部阶段性切片可以保留后续项，但不得把“当前不阻塞”写成“原功能不需要”。
- 纯前端数据/测试任务可由规划直接验收，但必须在任务行明确。
- Reviewer 验收通过或失败后都先把结论交回规划，不直接修改为 `done`、`ready` 或解锁下一任务。
- 规划审核验收通过：原任务改为 `done`、清空 Current actor；输入齐全时由规划解锁并通知下一任务。
- 规划审核验收失败：保持原 Owner，递增 Rev，退回 `ready` 并由规划写明失败证据、复验标准和停止边界。
- 确实缺少另一角色的新交付物时，新增独立任务，原任务保持 `blocked`，不得把责任转给用户传话。

## 14. 快速唤醒用语

固定角色以后只需要接收同一句话：

> 读取项目级 AGENTS.md、docs/WORKFLOW.md 和 docs/status/CURRENT.md；只处理 Current actor 指向你的当前动作，并按同步协议写回。没有可执行任务则停止，不自选工作。

角色名称必须明确为“规划对话”“UI 设计对话”“后端开发对话”或“前端开发对话”。用户不需要复制任务内容。

快速唤醒发出后，发送方仍须读取目标任务状态并确认送达；本段用语不能替代第 12 节的送达闭环。

## 15. 冲突与紧急停止

- 用户最新明确要求高于本地文档；规划负责先同步权威文档和看板。
- UI 与接口状态冲突时，以规划确认的文档契约为语义来源、以 `packages/contracts/` 为代码接口来源；不一致时停止集成并退回对应 Owner。
- 发现别的角色正在修改自己计划触碰的同一文件时立即停止，重读看板并报告冲突。
- 同一根因连续两次修复失败时停止叠加补丁，由规划重新检查数据流、状态源和任务边界。
- 达到任务验收后立即停止，不顺带开发下一任务。

## 16. 专业异议与冲突审查

四个角色都有提出异议的责任。UI 设计可以指出产品流程不清，后端可以指出状态或成本不可实现，前端可以指出 UI 与接口无法对接，规划也可以退回缺乏业务证据的技术设计。提出异议不等于获得改方案授权。

### 16.1 提交方式

发现下列问题时，当前角色停止受影响部分，把自己的任务改为 `blocked`、`Current actor=规划对话`，保持原 Owner，并在任务行和日志写入“冲突审查请求”：

- **冲突类型**：产品规则、UI/交互、代码契约、数据所有权、性能/成本、安全/隐私、文件所有权或验收冲突。
- **当前依据**：对应权威文档、契约字段、UI 验收项或任务边界。
- **可复现证据**：页面动作、请求/响应、状态码、截图、测试或具体文件位置。
- **影响范围**：哪些任务、页面、接口、数据或成本会受影响。
- **最小建议**：建议改变什么，以及不改变会造成什么；不得夹带无关重构。
- **能否继续**：不受影响的部分是否仍可安全推进。

没有证据的“感觉不合理”可以作为讨论线索，但不能直接推翻已确认契约。涉及数据丢失、重复付费、权限泄露、错误覆盖、状态双源或无法回退时必须立即停线。

### 16.2 规划对话的主管审查

规划收到冲突后先做分类，不机械支持任何一方：

1. **实现缺陷**：产品和契约已清楚，只是实现不符合。规划把原任务定向退回 Owner，写明失败证据和复验标准。
2. **文档/代码契约不一致**：规划确认权威语义；需要后端更新共享契约时新建或解锁 `BACK-*` 修正任务，依赖的前端保持阻塞。
3. **UI 与技术路径冲突**：规划召集 UI、后端或前端分别给出约束，形成 2–3 个可执行选项，比较用户体验、开发量、性能、成本和长期维护。
4. **产品范围或用户体验取舍**：规划不能代替用户扩大范围或改变已确认流程，必须把具体选项、推荐和影响交给用户确认。
5. **局部机械裁决**：不改变用户可见行为、成本、数据含义或里程碑时，规划可以直接裁决并同步文档和任务，无需让用户传话。

规划的裁决必须写回：采纳了什么、拒绝了什么、依据是什么、影响哪些任务、谁下一步动作、如何验收。重要决策写入相应权威文档；聊天结论不能替代本地写回。

### 16.3 复议和最终取舍

- 原提议角色在新证据出现时可以复议一次；必须补充新事实，不能重复同一意见。
- 同一冲突两轮仍无法在已确认范围内解决，或明显改变成本、体验、数据策略时，`Current actor` 转为用户，由规划与用户共同选择。
- 用户作出取舍后，规划一次性更新权威文档、任务依赖和所有受影响角色；用户不需要逐个对话传达。
- 任何角色收到裁决后只执行被确认的最小范围；不同意但没有新证据时不得另建平行实现。

## 17. 基础设施故障分流

项目协作中的服务不可用和本机执行失败必须先分流，再决定是否继续派发：

| 现象 | 归类 | 处理 | 禁止 |
| --- | --- | --- | --- |
| 模型网关返回 503、自动审查提示无可用上游 | `provider_blocked` | 记录网关域名、模型、协议和 `request_id`；同一请求最多受控重试一次，之后暂停相关交接并修复网关/模型映射 | 把 503 写成业务缺陷、无限重试、继续堆 FIFO |
| 普通仓库编辑触发 `auto_review` | `approval_route_blocked` | 检查工作区是否为 `workspace-write`；范围内编辑改走本地直写，规划记录路由异常 | 为普通编辑反复申请审批或要求用户逐次确认 |
| `CreateProcessAsUserW failed: 5`、PowerShell/执行器无法启动 | `executor_blocked` | 停止同一命令重试，保留当前任务状态，待宿主执行器恢复后续接 | 改业务代码、误标 `permission_blocked`、用业务重试掩盖宿主故障 |
| 目标固定对话确实为 `read-only` 或根目录不在可写范围 | `permission_blocked` | 规划修正权限或重新派发，收到 `permission_ok` 后再运行 | 把权限故障写成实现失败 |

每次报告都必须分别写明“状态已写回、唤醒已发送、送达/运行态已确认”；若基础设施分类尚未确定，保持 `notification_pending`，不得宣称交接完成。
