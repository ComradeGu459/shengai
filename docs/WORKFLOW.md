# 三对话协作与接力协议

状态：生效  
最后更新：2026-08-12

## 目的

让规划、UI 和开发三个对话共享同一套本地事实，各自只做职责内工作，并能在完成后把明确的输入交给下一角色。聊天记录可以辅助理解，但不作为项目状态源。

## 三个固定角色

| 角色 | 负责 | 不负责 | 主要交付物 |
| --- | --- | --- | --- |
| 规划对话 | 产品需求、范围、优先级、成本与技术方案比较、里程碑、验收标准、风险和最终取舍 | 编写业务代码、私自购买资源、替 UI 完成详细页面 | `PRODUCT.md`、里程碑、契约、ADR、`CURRENT.md` 分派 |
| UI 对话 | 信息架构、流程页面、设计变量、组件、交互状态、响应式与可访问性、预览和截图验证 | 改后端状态含义、决定云服务、实现付费接口 | `DESIGN.md`、UI 原型或前端展示层、UI 验收记录 |
| 开发对话 | 数据库、API、上传、Worker、前后端功能、测试、构建和技术实现日志 | 擅自改变产品范围、重新设计视觉系统、顺带实现下一里程碑 | 源码、迁移、测试、技术 ADR、真实验证结果 |

遇到边界问题时的默认归属：

- “做什么、先做什么、是否值得做”交给规划对话。
- “怎么展示、怎么操作、页面是否清楚”交给 UI 对话。
- “怎么存储、怎么调用、怎么恢复、怎么测试”交给开发对话。
- 同时涉及两类时，前一个角色先给约束和交付物，后一个角色再执行；不得各自假设一套答案。

## 唯一任务看板

`docs/status/CURRENT.md` 是唯一当前任务看板。每项任务只允许一个 `owner`，状态只使用：

- `blocked`：输入或授权不足，不能开始。
- `ready`：输入齐全，可以领取。
- `in_progress`：已有一个对话正在处理。
- `review`：交付完成，等待指定角色或用户验收。
- `done`：已验收，不再重复。

任务最小字段：`id`、`owner`、`status`、`goal`、`inputs`、`deliverables`、`acceptance`、`next_owner`、`blockers`。

同一任务不能同时属于两个角色。若确实需要两类工作，拆成有先后关系的两个任务，例如 `UI-M2-01` 完成后再让 `DEV-M2-01` 使用其交付物。

## 每个对话的启动动作

1. 读取 `AGENTS.md` 和 `docs/status/CURRENT.md`。
2. 根据任务中的 `inputs` 只读取必要权威文档，不扫描全部历史文件。
3. 明确回复：“我的角色、领取的任务编号、这次会交付什么、明确不做什么”。
4. 将任务从 `ready` 更新为 `in_progress`；如果不是本角色或状态不是 `ready`，不开始实现。

## 每个对话的结束动作

1. 运行与风险相称的真实验证，不把计划写成完成。
2. 在 `docs/logs/DEVELOPMENT_LOG.md` 追加日期、任务编号、实际修改、验证结果和未完成项。
3. 更新 `CURRENT.md`：任务状态、交付物路径、验收结果、阻塞项和 `next_owner`。
4. 如果下一任务输入已经齐全，将下一任务改为 `ready`；否则保持 `blocked` 并写明只缺什么。
5. 未经用户授权，不通过“交接”自动触发提交、推送、部署、购买或外部消息。

## 快速唤醒用语

新开或继续一个对话时，用户只需要说明角色，不必重复完整背景：

> 你是本项目的规划/UI/开发对话。先读取 `AGENTS.md`、`docs/WORKFLOW.md` 和 `docs/status/CURRENT.md`，只领取分派给你的 ready 任务；完成后按接力协议更新本地文件。

如果对话已经固定角色，用户以后只需说：

> 读取 CURRENT，继续你的下一项任务。

## 冲突处理

- 用户最新明确要求高于本地文档；发生变化时先由规划对话更新范围与看板，再交给其他角色。
- UI 与接口状态冲突时，以 `docs/contracts/` 的后端状态含义为准，由 UI 调整呈现；若状态本身不满足产品需求，退回规划对话裁决。
- 开发发现方案无法实现或成本明显变化时，不私自换范围；记录证据并把任务转为 `blocked`，交回规划对话。
- 同一文件被另一个对话改动时，先读取最新内容并保留对方工作，不覆盖、不恢复旧版本。
