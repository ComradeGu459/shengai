# ADR-0001：M2 采用对象存储分片直传与后端状态所有权

状态：已接受  
日期：2026-08-12

## 背景

系统预计不超过 10 名员工，但可能同时处理 5–6 个项目或上传批次，单项目或批次可达到 10–30 GB。若文件经过应用服务器中转，网站服务器带宽、连接数和临时磁盘会成为不必要的瓶颈，也会提高扩容和故障恢复成本。

## 决策

- 浏览器使用短时、限范围授权把分片直接传到 S3 兼容对象存储。
- 应用后端只创建上传会话、生成对象键、签发授权、确认分片、发起完成、校验对象并维护业务状态，不代理文件字节。
- PostgreSQL 是项目、素材、上传会话和清理任务的唯一业务状态源；对象存储只拥有文件字节。
- “暂停”是浏览器行为，不新增服务端暂停状态；恢复依据服务端已确认分片进行。
- M2 先使用数据库任务状态和有界 Worker 完成回收清理，不因未来可能扩容提前引入消息队列。
- 存储厂商保持可替换，但只支持一个经过选型的 S3 兼容实现，不同时维护多套供应商代码。

## 后果

### 正面

- 网站服务器无需承载大文件流量，可独立扩展 Web/API 和存储能力。
- 上传中断后能够只补传缺失分片。
- 数据库状态、对象存储状态和浏览器展示状态边界明确。

### 代价

- 必须处理跨域、短时授权、分片清单、校验值、会话过期和未完成分片清理。
- 浏览器刷新后通常需要用户重新选择同一文件，随后通过文件指纹核对再继续。
- 必须建立孤儿数据核对，处理“数据库有记录但对象缺失”或“对象存在但数据库无引用”。

## 被否决方案

- 由应用服务器接收并转发全部文件：会把 10–30 GB 上传压力集中在 Web 服务，不采用。
- M2 直接拆成上传微服务：当前只有一个真实业务切片，没有独立部署和团队边界证据，不采用。
- 只在浏览器保存上传状态：刷新、换设备或本地数据丢失后无法获得权威结果，不采用。
